# P5 — Deploy and cache

This is the stage where a correct change takes a site down, and where a successful-looking command does nothing at all. Both have happened here, in production, within one week of each other.

The deploy is not the upload. The deploy is the sequence **backup → upload → lint → purge → verify**, and it is only finished when verification passes on the URL a visitor actually requests.

## Input

- **The edited file, tested locally.** A template that was never rendered locally is a template whose syntax errors you are about to discover in production.
- **Credentials in environment variables**, never in the script and never on the command line where they land in shell history.
- **A written list of cache layers** between the origin and the visitor. Page cache plugin, reverse proxy, CDN. You need to know every layer you have to purge, in order.
- **A known-good rollback point**, meaning a backup you have actually restored once. An untested backup is a hypothesis.
- **The ability to see the origin**, so verification can bypass the CDN. Without it you cannot tell a cache problem from a code problem.

If the file you are deploying is a pricing, spec or legal template, get a second reader before the upload, not after.

## Deliverable

1. **A deploy log per operation**: timestamp, source file, destination, backup path, `php -l` result, purge result per layer, verification evidence.
2. **A one-line rollback command**, recorded in the same log.
3. **A verification artifact** — status code, response headers showing cache state, and a screenshot at desktop and mobile width.
4. **A drift correction**, when the edit originated on the server: the tracked copy updated in the same session, before the session ends.

"Deployed" is not a deliverable. The log is.

## The sequence

```
1. Local edit
2. Remote backup with a readable suffix
3. Upload to a temporary path
4. php -l on the uploaded file
5. Move into place
6. Purge page cache and reverse-proxy cache, on the right port
7. Verify with a bare URL and a browser user agent
8. Record what changed
```

Skipping step 2 makes step 7 unrecoverable. Skipping step 4 turns a typo into a white page. Skipping step 6 makes step 7 lie to you.

## Permissions: the rule that took a site offline

**Directories need the execute bit. `chmod -R 644` removes it.**

When a directory loses execute permission, PHP cannot traverse into it. WordPress does not crash — it falls back to a bare render that returns HTTP 200. The result:

- Every URL returns 200.
- Every file passes `php -l`.
- Every file has plausible permissions (`644` on a file is normal).
- The site looks broken in a way that points at code, CSS, or a plugin.

An hour can go into reading logs for a PHP fatal that never happened. The actual diagnostic is one command:

```bash
stat -c '%a %U:%G %n' /path/to/wp-content/themes/child-theme
# 644  ← wrong. Directories are 755.
```

Correct fix, and the form every deploy script must use:

```bash
find /path/to/theme -type d -exec chmod 755 {} \;
find /path/to/theme -type f -exec chmod 644 {} \;
```

Note the two commands. A single `chmod -R` cannot set different modes for files and directories, which is exactly why it produced this outage. See `scripts/fix_permissions.py`.

**Triage order when the whole site renders wrong but returns 200:** check the theme directory permission first, before reading a single line of PHP.

## Two cache layers, one of which lies

A typical WordPress host with a reverse proxy has:

1. **A page cache plugin** (Breeze, WP Rocket, LiteSpeed, etc.) storing rendered HTML.
2. **A reverse proxy** (Varnish, or a CDN) storing full responses in front of PHP.

Purging the first does not always purge the second, and hosts vary in whether the plugin's purge command reaches the proxy.

### The purge that returns 200 and does nothing

```bash
curl -s -o /dev/null -w '%{http_code}' -X PURGE http://example.com/
# 200   ← meaningless
```

Port 80 usually answers with a 301 redirect to HTTPS. A redirect is generated by the web server before the request reaches the proxy, and it does not carry the `PURGE` method. The `200` in the output is the redirect's target response, or the server's generic answer — not a confirmation that anything was invalidated.

Send the purge to the origin on 443, and make sure DNS resolution does not send it to a CDN:

```bash
curl -sk -X PURGE \
  --resolve example.com:443:127.0.0.1 \
  https://example.com/path/
```

`--resolve` pins the hostname to the origin IP, so a CDN in front cannot absorb the request. Without it, a proxied domain sends `PURGE` to the CDN, which does not forward that method, and you get a `200` for a request that never touched your server.

### Why verification needs a bare URL

**A cached response never executes PHP.** Any verification that bypasses the cache — a query string, a `Cache-Control: no-cache` header, an admin session cookie — tests the origin and tells you nothing about what visitors see.

Verify the way a visitor arrives:

```bash
curl -sk -A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 \
  (KHTML, like Gecko) Chrome/124.0 Safari/537.36" \
  https://example.com/products/ -o /tmp/v.html -w '%{http_code}\n'
```

Then assert on content, not just status: count the items, grep for a string that only exists in the new version, compare against the previous response.

### Confirming cache state

When available, read the cache header:

```bash
curl -sI https://example.com/ | grep -i 'x-cache\|age\|cf-cache-status'
```

`HIT` with a large `age` means you are looking at an old response. If a purge is followed by `HIT` and an unchanged `age`, the purge did not land.

## Working with wp-cli

Run `wp` with the working directory already inside the WordPress root:

```bash
cd /path/to/public_html && wp cache flush --allow-root
```

Do not pass `--path=` when the current directory is already correct. On hosts with `open_basedir` restrictions or a chrooted SFTP user, the flag resolves against a different path than the shell sees, and `wp` reports the install as missing while the same command works from the directory. This wastes time in exactly the moment you are already debugging something else.

If the host runs a containerised stack, `wp` may need the container's user context. Check `wp --info` before assuming a command failed because of the change you made.

## Backup and rollback

Back up remotely, with a suffix that says what the backup is for:

```bash
cp themes/child/products-data.php themes/child/products-data.php.bak-xx123
```

`bak-last` is acceptable for a deploy script's automatic safety copy. A named backup (`bak-415`, `bak-20261114`) is required for a change you might need to explain to a human later.

Rollback is one command:

```bash
cp themes/child/file.php.bak-tag themes/child/file.php && rm themes/child/file.php.bak-tag
```

Keep the backup until verification passes. Keep the named one for a month.

## Staging and production drift

If edits happen in two places — a local tracked copy and a live server — they will diverge. The divergence is always invisible until a page loses a feature nobody remembers removing.

The rule: **any edit made on the server gets written back to the tracked copy in the same session.** If a fix was applied through a file editor on the host, download it, diff it against the local copy, and commit. The cost is two minutes; the cost of drift is a weekend.

## Checklist

- [ ] Remote backup exists with a readable suffix
- [ ] Uploaded to a temporary path first, not overwritten in place
- [ ] `php -l` clean on the uploaded file
- [ ] Permissions: directories 755, files 644, verified with `stat`
- [ ] Page cache purged
- [ ] Reverse-proxy purge sent to 443 with `--resolve`, response code recorded
- [ ] Second purge request shows a cache `MISS` or a decreased `age`
- [ ] Verified with bare URL and browser user agent
- [ ] Content assertion passed (count, marker string), not just status 200
- [ ] Both 1440 px and 390 px screenshots taken
- [ ] Named backup retained, change recorded
- [ ] Any server-side edit written back to the tracked copy

## Failure modes

| Symptom | Cause | Where |
|---|---|---|
| Whole site renders wrong, every URL 200, lint clean | Directory permission lost execute bit | `90` F-01 |
| Deploy reported success, page unchanged | Purge swallowed by a 301 on port 80 | `90` F-02 |
| Change visible to admin, not to visitors | Verified with a cache-bypassing session | `90` F-25 |
| `wp` says "not a WordPress installation" | `--path` resolved through a chrooted SFTP path | `90` F-26 |
| A page lost a section weeks after launch | Staging/production drift | `90` F-19 |
| 500 on one page after an edit, others fine | Syntax error in one template file | `90` F-27 |

## Anti-patterns

**"It works on my machine."** There is no local copy of a live WordPress site that matches production. Verify on the live URL.

**Purging and immediately curling once.** Some proxies invalidate asynchronously. Request twice, then assert on the second response.

**Editing the live file through SFTP and calling it deployed.** No lint, no backup, no purge. It works until it does not, and then there is nothing to roll back to.
